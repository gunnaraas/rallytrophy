# Range 0x44b930 - 0x44ea5f: module map (read-only raw disassembly, Patch 1.01 exe; no REA)

Method: rawdis.py over the whole range, refs.py for callers/abs refs, .rdata strings/floats/vtable read with the PE section reader, a look at the Game ctor/dtor (0x430440-0x4306b0, 0x43090f-0x4307e0) for the owners. "Guess" marks inference. EH handler addresses (0x4d9d48 ... 0x4da003) are the `push imm` after `push -1` in each SEH prologue.

## 0. Headline findings

1. **The range is two files.** File A (0x44b930 - 0x44d25f) is a `MenuScreen` subclass, the **replay-list screen** ("ReplayMenu", guess for the name; it lists files from `savegame/replay`, see below). File B (0x44d260 - 0x44ea5f) is the **save-game / career file code**: the methods of the heap object at `Game+0x2dcc` (header record + career state, saved to `savegame/<mode><n>.SAV` and `savegame/relay.sav`). The slot menu in the next range (0x44ea60) is its client.
2. **File boundaries**: previous file ends with the `_$E` guard stub at 0x44b900; File A ends with its stub at **0x44d230** (48 bytes, 0x44d230-0x44d25f); File B ends with its stub at **0x44ea30** (48 bytes, 0x44ea30-0x44ea5f, followed by SlotMenu's ctor at 0x44ea60). Stub shape: `mov cl,[0x5826d5]; mov al,1; test al,cl; jne; or cl,al; mov [0x5826d5],cl; jmp +; push 0x402c90; call atexit(0x4c0d01); pop ecx; ret`. Neither file has file-scope statics (no initialiser pair) and neither defines STL template instances (all string work is out-of-line calls to 0x402700/0x402ab0/0x402980/0x402960/0x403ba0/0x404ba0 or inline expansions).
3. **functions.csv lists 16 functions, there are 17**: it is missing **0x44ba30** (452 bytes, vtable slot 1, `Setup(Game*)`, no SEH, `ret 4`). It is not folded into a neighbour; the gap between 0x44b9c0+102 and 0x44bc00 is exactly 0x44ba30 plus its alignment padding. Everything else between the stubs is accounted for (17 functions + 1 stub each side).
4. **File A object layout is the same shape as SlotMenu's** (include/unk_44ea60.h) with only **two** labels instead of ten: size **0x3e8**, embedded in Game at **Game+0x29e4** (Game ctor 0x430475 `lea ecx,[esi+0x29e4]; call 0x44b930`; dtor call 0x43091f `call 0x44b9c0`; next members: Game+0x2dcc and Game+0x2dd0 are pointers, 0x2dd4 is the next embedded member). 0x29e4 + 0x3e8 = 0x2dcc.
5. **Game+0x2dcc is a `new`ed object of 0x614 bytes** (Game ctor `push 0x614; call 0x4c1276; mov ecx,eax; call 0x403c90` (ICF'd `mov eax,ecx; ret` ctor) at 0x4305ab-0x430686) and **Game+0x2dd0 a `new`ed object of 0x70 bytes** (0x43067f push 0x70, same trivial ctor). Both freed in Game's dtor (0x4307b1 / 0x4307d1: `call 0x48e660; delete`). Name guesses: `SaveGame` (0x2dcc, header + career state) and `ReplayRecord` scratch (0x2dd0: used by ReplayMenu as `0x403ca0(idx)` / `0x404930(idx, record*)`, both in the earliest TU of the program, not in this range). File B's 0x44d260/0x44d6a0/0x44deb0/0x44e3e0/0x44e650/0x44e960 take `this` = the 0x2dcc object; 0x44e6a0 is a plain function (never reads ecx).
6. **No vtable in File B.** File A has one vtable at **0x4e19c4** (read from .rdata): slot 0 = 0x44b9a0 (scalar deleting dtor), slot 1 = 0x44ba30 (Setup), slot 2 = 0x43ff80 (shared `MenuScreen::Release`, ICF'd with the other screens), slot 3 = 0x44cfb0 (Draw). Right after the vtable (not slots): floats 262.0 (0x43830000) and 42.0 (0x42280000) used by the code as `[0x4e19a0]`/`[0x4e19a4]`.

## 2. FB: SaveGame file code, 0x44d260 - 0x44ea5f

`this` for the thiscall functions = the 0x614-byte object at `Game+0x2dcc` (callers: Game ctor area 0x42ef28 / 0x42f299 (`mov ecx,[edi+0x2dcc]; push idx-2; call 0x44d6a0`), 0x43327a (`call 0x44deb0`), 0x4338a5 / 0x4339a5 (`call 0x44e3e0`), 0x492d6b (`call 0x44e650`), 0x44f15a / 0x44f5cc (SlotMenu: `0x44d260`), 0x45094f (SlotMenu::RefreshSlots: `0x44e6a0`)).

### Object layout (SaveGame, 0x614 bytes; seen in this file)
- **+0x00 .. +0x6b: `SlotRecord` header (0x6c bytes)**, the same record that SlotMenu holds eight of (stride 0x6c). Written by `FillHeader` (0x44e960) from the live race state, read/written verbatim by SaveSlot/LoadSlot/GetSlotInfo after two 4-byte magic words. Fields: +0x00..0x1f char name (set elsewhere, the slot menu copies the edited name here), **+0x20 int count** = `RaceMode.vec(+0x18..+0x1c).size()` (number of "player"-type entries; LoadSlot uses it as the count of the first player loop), +0x24 int = `Game+0xd40 + 1`, +0x28 int = `Game+0xd44 + 1`, +0x2c int = global `0x50132c`, **+0x30 SYSTEMTIME** (`GetLocalTime`, IAT 0x4e10b0, 16 bytes) -> shown as date/time in the slot menu, +0x40 = `Player0.f1a5c`, +0x44 = `Player0.f1a60` (Player0 = `RaceMode.+0x24`), +0x48 char[...] = copy of the string at Player0+0 (stage/player name), **+0x68 int** = (all players = RaceMode `+0x8..+0xc` count) - (+0x20 count) = number of the remaining players (LoadSlot's second loop). The `kind`/flag word +0x20 that the SlotMenu code tests as "0 = empty slot" is the same word: GetSlotInfo sets it to 0 when the file is missing.
- **+0x6c .. +0x610: career body, 0x5a5 bytes** (LoadRelay/SaveRelay copy `0x169` dwords + 1 byte to/from `this+0x6c`): byte flags **+0x8d** (byte), **+0x8e** (byte, set from SaveRelay arg 2), **+0x8f** (byte, reset to arg1 or incremented), **+0x90** (byte) lie inside it. Floats at `this + idx*4 + 0x58d` and 0x28-byte (10-dword) blocks at `this + idx*0x28 + 0x69` are written by `SaveStats` (0x44e650). Offsets are relative to the object, not the body. Guess: championship progress (per-rally times, standings).
- File magics: **slot files** start with `0x00008195`, then `0x20011010` (a date-looking version word), then the 0x6c header, then per-player records of 0x74 bytes; **relay.sav** starts with `0x63777472` (bytes `rtwc`), then `0x20020109`, then the 0x5a5-byte body and sizes; the relay body is passed through the **cipher at 0x4010f0 (encrypt) / 0x401180 (decrypt)** (XTEA-like: delta 0x61c88647, rounds from `0x34/n`, key string at 0x4fa2e4), the slot files are plain.
- Path building (all four loaders/savers): base = `savegame/arcade` (0x4fa30c) if global **0x501458 != 0**, else `savegame/rally` (0x4fa2fc); then `itoa(slot, 10)` (0x4c1902), then `.SAV` (0x4fa2f4); the special career file is `savegame/relay.sav` (0x4fa31c). (So 0x501458 selects the arcade/quick-race save set; the same flag guards AIDriver creation per range-49b630.md.) File API = `File` class of rallytrophy.h: ctor 0x4a4e00 `File(name, mode)` (mode 0x82 = write, 0x81 = read), `Write` 0x4a5e90, `Read` 0x4a5e00, `Close` 0x4a5d00, dtor 0x4a4d90, `Exists` 0x4a6050, `GetSize` 0x4a5ff0; the `File` object is `new(0x4078)`.
- Globals touched: 0x501450 RaceMode*, 0x501458 arcade flag, 0x501454, 0x50132c, 0x501334, 0x50145c, 0x501460, 0x501464, 0x501468, 0x501472 (byte; zeroed at the start of LoadRelay, set to 0 at its end), 0x501338 (array of player names, stride 0x1e = 30 chars, first entry `"Player 1"` at 0x501338 by default), 0x5013ec (dword array, one per player, step 4). LoadSlot copies each loaded player's name/id into these tables.
- Out-of-range callees: Player ctors 0x4909b0 (`Player(id, remote)`), 0x490b90 (`Player(int)` with `data/AI/ai1.ini` pushed, 0x4f8c84), 0x490c30 (`Player(kind, index)`), `Player::SetName` 0x490fb0 (this file is the biggest user: 0x44d8e6, 0x44da38, 0x44db7d, 0x44dd92, 0x44e0ca), `Player::FUN_00491130` 0x491130, `RaceMode::AddPlayer` 0x485f60, `Player+0x1c874` sub-object `Clear` 0x46bbc0 and `FUN_0046be50`, `0x443620` (reference time of a rally stage, called on `Game+0x3aec`), `0x48e660` (shared empty dtor), `0x401180/0x4010f0` cipher.

## 3. Compiler-generated / out-of-line pieces

- **0x44b9a0** scalar deleting destructor (vtable slot 0).
