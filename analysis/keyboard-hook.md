# Keyboard hook

`T_56b0bc` installs a thread-local `WH_KEYBOARD` hook on the first instance and unhooks it when the last instance is destroyed. Its constructor at `0x4b6e10` and destructor at `0x4b6f60` now both match exactly. On hook-install failure, the constructor builds and throws an `assertion_error` with the same 0x1c-byte layout as the mouse hook; the original duplicated error string, exception base, derived vtable, and throw sequence are recorded in `ev_7aa9067319519edcc15870c8abb12a16d5699c1b9ebbd804f2d1d1f75cf3a532`. The hook callback is `FUN_004b6f90` at `0x4b6f90`, referenced by the constructor. A shipped-binary byte read covers the full 773-byte callback body (`ev_6641e60793d9fe6db1f9c0c2d69d05ac75bcc9f20fab3782f0e4767acbdba657`); the callback entry reference is also observed in `ev_acd26114f61223753f305655ffdd0e7e96f96503d0a1b1e328ce9c7825f682af`.

The callback forwards negative hook codes, records key-down state in the high bit of a 256-byte table, toggles the low transition bit on accepted key-down messages, and maintains the number of currently held keys. It ignores autorepeat messages when repeat mode is disabled, and marks accepted keys in the per-frame key array. When character input is enabled, it translates A–Z using Shift/Caps state, passes digits through, and translates three OEM virtual keys before adding the resulting byte to a character deque. These behavior statements are a reconstruction from the observed callback bytes, not a verbatim Ghidra decompilation.

The character-queue gate at `0x4b701f` reads `DAT_0057bc5c`; an xref search found that instruction as its only direct code reference (`ev_af59647eab1ad15dac27a1555d7c87c98deddd72206177d9372199061ba9fd12`). The variable's initial value is not observable in the mapped PE data, so whether the shipped process enables this path remains unresolved.

`FUN_004b6f90` is implemented in `src/input.cpp` as a behavior reconstruction and remains `NONMATCHING` (768 built bytes versus 773 observed bytes). The callback's original deque storage and compiler-generated insertion path are not yet reproduced; the C++ implementation uses `std::deque<unsigned char>` to express the observed append behavior.
